# 调研报告：AI Agent「远程服务器开发」开源方案对比

> 日期：2026-08-15
> 背景：为 DSH「服务器开发 Agent 模式」（方案 B：preset 自包含远程执行层）做开源方案调研，回答核心问题——**主流的 AI 编码软件（Trae / Cursor / Claude Code / OpenHands 等）是如何实现"agent 在远程服务器上开发"的？** 我们的方案该借鉴谁、避开谁。
> 方法：WebSearch 检索官方文档 + 开源仓库 README/源码结构 + 社区深度拆解文章。

---

## 一、调研结论速览（TL;DR）

远程开发有 **4 条根本不同的技术路线**，代表产品/项目如下：

| # | 路线 | 代表 | 核心机制 | 对 DSH 的启示 |
|---|---|---|---|---|
| 1 | **服务端部署型** | Trae Remote-SSH、Cursor Remote-SSH、claude-remote-sync | 在远程装一整套服务端（或完整 CLI），本地只剩 UI/输入 | 最重，**不适合** DSH 插件（需改远程、装服务端） |
| 2 | **执行后端替换型** | DSH 官方 e2b、OpenHands Runtime、**本方案 B** | agent 核心留本地，把 shell/fs/terminal 的 provider 换成远程实现 | **正是我们要走的路线**，官方先例已验证 |
| 3 | **工具拦截转发型** | claude-remote (langwatch)、claude-remote-shell | 拦截 Bash 工具，命令经 SSH 转发到远程，文件靠 Mutagen 双向同步 | 可借鉴其**路径映射/同步 flush** 细节，但同步路线整体不推荐 |
| 4 | **单命令转发型** | remote-launcher | token 留本地，只把单条命令丢给远程执行 | 能力太弱，只适合批处理场景 |

**推荐度排序（对我们的方案 B 的参考价值）**：路线 2 源码 > 路线 3 细节 > 路线 1 交互 > 路线 4 反例。

---

## 二、路线详解

### 路线 1：服务端部署型（本地仅 UI）

**Trae Remote-SSH**
- 首次连接远程服务器时，自动在远程安装 **TRAE 服务端**（包含 AI 后端、代码引擎、终端、调试器、工作区插件等完整组件），本地仅保留 UI 壳
- 连接方式支持直接输入 `ssh user@host` 字符串，或从 `~/.ssh/config` 选择主机；支持密钥/密码认证
- 交互模式：**"模型请求本地发起、执行远程完成"**——agent 推理在本地，命令/文件操作全部落在远程真实环境

**Cursor Remote-SSH（Cursor 3）**
- 复用 VS Code Remote-SSH 协议，首次连接在远程安装 `~/.cursor-server/`
- Agent 模式可在远端**真实环境**里探测、推理、执行（跑终端、构建、调试）
- 本地 Cursor 进程负责模型请求，远端负责执行与文件系统

**claude-remote-sync（anhkhuong975，npm，MIT）**
- 在远程完整运行 Claude Code CLI（`--dangerously-skip-permissions`），通过 Mutagen 双向同步 `~/.claude` 配置与会话历史 + 项目文件
- 通过 SSH + tmux 把终端挂进远程会话；路径必须两端一致（会话 key 依赖绝对路径）
- 本质是"整个开发机搬上远程"，本地变成瘦终端

> **共同点**：远程要装完整运行时。对 DSH 而言 = 需要在服务器上装 DSH 服务端 + 把对话/会话状态迁过去——工程量巨大且违背插件形态。**只借鉴其连接交互设计（`ssh user@host` 输入）**。

### 路线 2：执行后端替换型（本方案 B 的同类）★ 核心参考

**DSH 官方 e2b POC（源码已本地验证）**
- `dsh-e2b`（沙箱生命周期所有者）+ `dsh-subprocess-e2b`（远程 subprocess provider）+ `dsh-fs-e2b`（远程 fs provider）
- 官方明确：agent/会话状态、LLM 请求、skill **全部留在宿主进程**，只有文件系统与进程管理通过 `ctx.e2b` 打到远程 Linux
- 这就是"provider 替换"的完整模板——**我们的 SSH 版 = 把 e2b 云沙箱换成 ssh2 连接**

**OpenHands Runtime（All-Hands-AI/OpenHands，MIT，SWE-Bench ~77%）**
- 核心抽象：`SandboxService` 接口（沙箱生命周期：创建/查询/暂停/恢复），三种实现：
  - `DockerSandboxService`：默认，Docker 容器内跑 **Action Execution Server**（初始化 `ActionExecutor`，含 bash shell + 插件）
  - `ProcessSandboxService`：本地进程（开发/单测用）
  - `RemoteSandboxService`：**远程沙箱**——官方一等公民，正是"agent 本地、执行远程"的架构
- 通信协议：Agent 发 **Action**（shell 命令/文件操作/Python 代码…），后端 `action_execution_client.py` 通过 REST API 打到容器内 server，server 执行后回传 **Observation**（含 cwd 状态）
- 安全：confirmation policy + risk analyzer（高危命令确认）
- 启示：**OpenHands 用 REST 抽象隔离了"执行在哪"，DSH 用 provider 抽象类（`ctx.shell`/`ctx.subprocess`/`ctx.fs`）做同样的事**——架构同构，我们的方案在 DSH 里天然成立

> **共同点**：agent 核心（对话、状态、LLM）留在本地，执行层通过抽象接口换成远程后端。**我们的方案 B 就是这个路线**，且有 DSH 官方 e2b 和 OpenHands 双份先例背书。

### 路线 3：工具拦截转发型（Claude Code 生态的民间方案）

**claude-remote（langwatch/claude-remote，MIT，18 commits）**
- 原理：拦截 Claude 的 **Bash 工具**（`$SHELL` 层替换），每条命令通过 SSH 转发到远程执行，保持相同的 cwd、stdout/stderr、exit code
- 文件同步：**Mutagen 双向同步**（曾试 SSHFS，性能差放弃）；命令执行前 flush 一次、执行后再 flush 一次
- 路径映射：本地路径 ↔ 远程路径自动翻译；追踪 Claude 的 cwd（`pwd -P >| /tmp/...`）；远程 `source ~/.profile` 补 PATH
- 持久连接：SSH ControlMaster 复用
- 最新提交：per-session offload isolation（按会话隔离）

**claude-remote-shell（torarnv）**
- 更彻底的拦截：**只有 Bash 工具被重定向到远程**，其余工具（文件编辑/写入/MCP）仍在本地执行
- 即"命令远程、文件本地"——与我们方案正好相反，是另一种取舍

**remote-toolkit（xieTwim）**
- Mutagen 同步 + SSH/tmux 命令 + 可选 Slurm（HPC 集群）；本地 replica 目录同步到远程后 CC 直接读写
- 明确警告：`rt sync flush` 返回 0 不代表两端一致（冲突/忽略路径照样 exit 0）——**同步方案的可靠性坑**

> **共同点**：不替换 provider，而是**在工具层拦截/同步**。优点是无侵入（不动 agent 核心）；缺点是**文件在两端各有副本**，存在同步延迟/冲突/大文件问题（remote-toolkit 自己都承认 flush 不可靠）。我们方案 B 的 SFTP 直连远程 FS 天然没有这个问题。

### 路线 4：单命令转发型（反例）

**remote-launcher**
- token 全程留在本地，只把**单条命令**通过 SSH 发到远程执行并回传结果
- 无文件同步、无持久 shell、无交互
- 仅适合"本地 agent 调度远程批处理"场景，**不是**服务器开发模式

## 三、横向对比表

| 维度 | ① 服务端部署（Trae/Cursor） | ② Provider 替换（e2b/OpenHands/本方案） | ③ 工具拦截+同步（claude-remote） | ④ 单命令转发 |
|---|---|---|---|---|
| 远程需要装什么 | 完整服务端（TRAE/cursor-server） | 无（SSH 即达） | 无（SSH 即达） | 无 |
| agent 核心在哪 | 本地（执行远程） | **本地** | 本地 | 本地 |
| 文件系统 | 远程真身 | **远程真身（SFTP）** | 本地副本+同步（有冲突风险） | 无 |
| 持久终端 | ✓ | ✓（PTY） | ✓（ControlMaster） | ✗ |
| 体验原生度 | 高 | **高** | 中（同步延迟/路径翻译复杂） | 低 |
| 对 DSH 的改动 | 大（需远程服务端） | **中（写 provider，复用 ssh2 引擎）** | 大（拦截 Bash + 同步层） | 小但无意义 |
| 安全 | 远程全权 | 远程全权（需高危命令确认） | 远程全权 | 远程全权 |
| 参考价值 | 交互设计 | **★★★★★ 架构模板** | ★★★ 细节借鉴 | ★ 反例 |

## 四、对 DSH 方案 B 的关键启示（修订方案书依据）

1. **路线选择被验证**：主流产品里，Trae/Cursor 走"服务端部署"是因为它们是闭源 IDE、可以控制远程端；**开源 agent（DSH/OpenHands）只能也必然走"provider 替换"**。我们的方案 B 是开源生态的标准解法，非孤例。
2. **分工参照 Cursor**："模型请求本地发起、执行远程完成"——正是 DSH e2b README 的"不是完整 harness 运行时"描述，也是我们方案 B 的边界（会话/LLM/skill 留本地）。
3. **连接交互参照 Trae**：首次连接直接贴 `ssh user@host` 字符串（或 `~/.ssh/config` 选择）——**与用户已确认的"首次对话输入连接"一致**，进一步支持这个交互设计。
4. **持久终端参照 OpenHands/claude-remote**：用 PTY + 持久 shell（状态跨命令保留），命令 cwd 追踪（claude-remote 的 `pwd -P` 技巧可用于远程 bash 的 cwd 保持）。
5. **安全实践（全生态共识）**：
   - 低权限专用用户 + 专用密钥（**私钥绝不给模型**）
   - 固定项目目录（OpenHands volume 思路）
   - 高危命令确认（OpenHands confirmation policy + risk analyzer；DSH permission 体系）
6. **避免的坑**：
   - **不要用文件同步路线**（Mutagen flush 不可靠、路径翻译复杂、两端副本心智负担）
   - **不要用单命令转发**（无持久性）
   - **不要给远程装服务端**（超出插件职责，且用户服务器不可控）
